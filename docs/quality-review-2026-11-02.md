# PR #5 修复与验证流程检视

日期：2026-11-02（Asia/Singapore）。范围：PR #5、仓库内验证/发布脚本、测试配置，以及 GitHub 默认分支的只读设置检查。不是整站安全认证，也不是正式生产验收。

## 本次结论

修复 PR 的两个失败点，保留 UI、原性能门槛及保存结果断言。测试通过不能替代生产准入：默认分支目前没有强制检查，用户已明确要求暂不修改仓库管理设置。

### 1. CSS：优化加载范围，保留 10,000 字节门槛

原始 CI 的 `styles.GOBot-pf.css` gzip 为 10,223 字节。10,000 是本项目的单文件预算，不是现代网站的通用标准。最初尝试上调至 11,000 的修改已撤回，没有发布。

申请卡样式原本进入所有页面的公共 CSS。本次沿用 `pageStylesheets` 的页面资源机制，只在出现 Cloudflare/Firebase 申请卡时加载该样式；隐藏的 Firebase 卡不加载。后台预览使用相同机制。样式声明本身未修改，新文件也有内容版本，避免缓存错配。

| 指标                                    |         修复前 |   修复后 |
| --------------------------------------- | -------------: | -------: |
| 公共 CSS gzip                           |       10,223 B |  9,338 B |
| 申请卡独立 CSS gzip                     | 包含在公共包内 |  1,326 B |
| 首页直接引用 CSS 合计（含字体声明）     |       11,209 B | 10,324 B |
| 申请卡页直接引用 CSS 合计（含字体声明） |       15,893 B | 16,334 B |

拆分使普通页面少下载 885 B；卡页增加一个请求和约 441 B 压缩开销。这是按功能加载的取舍，不是全站每页都变小。总量不包括字体二进制、图片和运行时新增资源，不能当作完整网络传输量。

`audit:output` 仍拒绝任意超过 10,000 gzip 字节的 CSS，并新增实际大小、上限、每页引用文件及总量报告，避免只看小文件而忽略总开销。反向检查验证了超限文件仍会失败。

### 2. 图片测试：修复错误的选区前置条件

CI 的图片请求成功，输入后保存的数据却变成新段落 ` changed` 加原 `Image caption`，图片消失。Trace 中出现了 `ProseMirror-selectednode`。

旧测试仅比较 `getSelection().anchorNode.textContent`。整个编辑器容器也可能返回 `Image caption`，因此不能证明光标在 caption 文本里。段落中心点击还受滚动和布局影响。

该用例的目标是图片显示和公开 URL 的持久化。本次使用浏览器原生 Selection 将光标放在 caption 文本末尾，检查文本节点、折叠状态、偏移和焦点，再发送真实键盘事件并保存。图片 URL、不得保存 `/admin/api/assets/`、caption 更新三个最终断言均保留。

这稳定了持久化测试的准备步骤，不等于证明所有字体加载时序下的鼠标命中均正确。实际编辑操作仍由其他浏览器交互测试覆盖；不得据此删除用户点击行为测试。

### 3. 防止 CI 只运行部分测试却变绿

Playwright 配置新增 `forbidOnly: !!process.env.CI`。通过临时 `test.only` 用例验证 CI 会退出失败。Vitest 已默认在 CI 禁止 `only`，没有重复改配置。

### 必须在宣称生产门禁完整前处理

1. **默认分支缺少强制检查。** GitHub 只读 API 返回 `gh-pages.protected=false`、状态检查关闭、分支规则列表为空。`verify` 和三个浏览器任务失败不会由仓库规则强制阻止合并。`deploy:studio` 核对默认分支 SHA 并运行本地 verify/output，但不核对该 SHA 的完整浏览器检查；公开发布工作流也没有显式核对 Verify 成功。建议先启用用户已审阅的 PR/四项检查规则，再设计对冻结源码 SHA 的发布准入验证，兼顾已发布旧版本回滚。用户要求暂不修改设置，本次没有启用保护或更改发布权限。

### 应补齐，但不能用本次绿灯掩盖

2. **性能采样不完整时可能仍通过。** `audit-performance.mjs` 丢弃失败运行；默认三次中只有一次成功时仍可能使用那一次作结果。应要求足够的有效样本，区分环境失败和性能不达标，并保留失败原因。本次实测每页均完成三次，未触发该缺口。

3. **综合性能分不能代替单项指标。** Research 的实验室 LCP 为 2.86 s，即使综合分 95 通过仍有加载优化空间。应先分析关键图片、字体和加载顺序，再根据固定测试环境设定可重复的单项预算；线上另看移动/桌面第 75 百分位 LCP、INP、CLS。当前没有证据支持声称线上 Core Web Vitals 全部良好。

4. **恢复演练没有持续进入 CI。** 可在隔离数据库的 Chromium 集成测试之后复用 `backup:rehearse`，保存恢复验证结果；不能把本地 SQLite/D1 演练等同于生产 R2/D1 灾难恢复。

5. **真实渲染与辅助技术仍有覆盖边界。** 现有 Linux WebKit 测试夹具为 CPU 性能关闭 backdrop blur，Chromium、Firefox 与本机 WebKit 保留。此次本机模糊断言通过，但 Linux WebKit 绿灯不能证明 Safari 真机玻璃效果。应安排真实 Safari/iOS、Android，以及 VoiceOver/TalkBack/NVDA 的关键流程验收；未引入未经设计确认的截图基线。

## 如何随产品升级调整门槛

不要把 10 KB CSS、14 KB HTML、95 分、100 分当成通用商用认证。它们是项目选择，应由目标设备/网络、真实用户指标、页面类别和历史基线支撑。

安全边界、数据完整性、关键流程、可访问名称和键盘操作不因功能增加而放宽。体积预算可在确有新增需求、已排除无用资源、测量了整体成本后调整，并记录基线和理由。长文章内容增长与公共脚本膨胀也应分开判断。不要以单个偶发低分调整预算，也不要靠增大等待、跳过断言或全局重试掩盖失败。

后续顺序：先补生产合并/发布准入，再补性能采样完整性和恢复演练，随后建立真机验收与线上体验基线。当前站点测试基础较完整，但尚不能据此称为已完成成熟商用验收。

代码定位：资源加载见 `packages/presentation/src/page-assets.ts`、`scripts/build-presentation.ts`；产物门禁见 `scripts/audit-output.ts`；图片回归见 `tests/independent/editor-boundaries.spec.ts` 的 IND-05；无障碍例外见 `tests/browser/accessibility.spec.ts`；发布准入见 `.github/workflows/publish.yml`、`scripts/deploy-studio.ts`、`scripts/deployment/source.ts`；采样规则见 `scripts/audit-performance.mjs`；恢复演练见 `scripts/restore-rehearsal.mjs`。
