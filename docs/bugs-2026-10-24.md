## AUD-01：长中文文件名使素材库崩溃

**复现：** 上传一张有效 JPEG，文件名使用 50 个中文字加 `.jpg`；随后进入 Image library。上传成功，但素材库渲染抛出 `URI malformed`。

**原因：** 前端对文件名执行 `encodeURIComponent`，后端直接截取编码后字符串的前 200 个字符，可能截断百分号转义或一个 UTF-8 字符。素材库再次 `decodeURIComponent` 时没有容错。

**影响：** 文件名写入数据库，重新打开素材库仍可能触发错误。它不是只出现一次的上传提示问题；图片二进制本身可以完全正常。此次只污染隔离测试数据库，未向正常预览素材库写入该文件。

**位置：** `apps/studio/server/index.tsx:140`、`apps/studio/editor/MediaLibrary.tsx:29`、`apps/studio/editor/main.tsx` 的 `upload`。

**建议修复：** 服务器先安全解码和规范化文件名，再按 Unicode 字符限制长度，以普通文本保存；前端不假定数据库名称必然是合法 URI 编码。对素材卡片增加错误隔离，避免一个异常记录导致整个界面失效。修复后处理已经保存的损坏名称。

**验收：** 中文、emoji、`%`、长名称均可上传并打开素材库；同一界面的其他图片仍能显示。自动化证据见 `tests/audit/findings.spec.ts` 的 AUD-01。

## AUD-02：上传成功不代表图片可用

**复现：** 向上传 API 提交以 `FF D8` 开头、长度 16 字节的内容。预期拒绝，实际返回 HTTP 200，并分配素材 URL。将相同内容交给项目使用的 Sharp 解码，报 `JPEG datastream contains no image`。

**原因：** 接口只检查文件大小和少量格式标记，没有验证图片能够完整解码。真正解码发生在发布素材构建阶段。

**影响：** 管理者会收到“上传成功”，随后遇到破图；如果在页面中引用该素材，发布构建会在解码阶段失败。本轮验证了接口接受和解码失败，没有执行真实生产发布。该接口受身份验证保护，不能据此宣称发现了未登录远程执行漏洞。

**位置：** `apps/studio/server/index.tsx:113` 起；`scripts/build-assets.ts` 的上传素材处理循环。

**建议修复：** 增加可信的图像解码/验证阶段，校验尺寸、像素总量与格式，并在验证完成前禁止将素材作为可发布图片使用。不能简单将 Node 原生 Sharp 直接搬进 Worker；应选择适合运行环境的校验实现，或明确的待验证素材流程。发布检查仍保留第二道校验。

**验收：** 截断 JPEG/PNG/WebP、格式标记伪造、过大像素图均得到明确错误；普通照片上传、预览和发布正常。自动化证据见 AUD-02。

## AUD-03：Blog 的删除使文章集合失去入口

**复现：** Blog → Page settings → Delete page，确认后保存，刷新后台。已有文章仍在数据库，但正常导航中没有 Articles 集合，也无法选择这些文章。

**原因：** 顶层页面列表始终过滤文章和日期归档；Articles / Archive views 入口又完全依赖某个含无日期过滤 archive 区块的页面。删除这个页面后，没有独立的集合入口或一致性保护。

**影响：** 现有 6 篇文章及归档的日常管理中断。不是数据库记录被删除；可以通过恢复版本或重建相应 Blog 入口找回，但不能要求管理者懂内部区块规则才能继续编辑。删除最后一个 Blog 列表区块也有同类结构风险，本轮自动化直接验证的是删除 Blog 页面。

**位置：** `apps/studio/editor/page-model.ts:16`、`apps/studio/editor/PageEditor.tsx:71` 及页面删除操作。

**建议修复：** 将“文章集合”与“展示该集合的 Blog 页面”分开建模。保留集合的稳定管理入口，同时满足用户要求的文章归组；删除展示页时清楚说明影响。或者在唯一入口删除前强制选择迁移目标，不能静默隐藏文章。

**验收：** 删除、取消发布、改变 Blog 区块后，已有文章仍能列表检索、编辑和发布。自动化证据见 AUD-03。

## AUD-04：保存正文会移除标题锚点

**复现：** 在内容中放入带 `attrs.id = "stable-section"` 的二级标题，进入后台只修改其后的普通段落并保存。读取保存结果，标题 ID 已变成 `undefined`。

**原因：** 内容模型和公开渲染器支持标题 ID，但 Tiptap 的 Heading 扩展没有注册此属性。文档经过编辑器序列化后，属性被丢弃。

**影响：** 发布后，原先指向 `#Education` 等标题的深链接可能失效。当前种子内容实际有 **8 个标题锚点**，因此不只是虚构未来字段的边界问题。当前静态构建的 360 个站内链接检查通过，并不能证明编辑后仍保留这些锚点。

**位置：** `apps/studio/editor/RichEditor.tsx:18`、`packages/presentation/src/rich-text.tsx:34`。

**建议修复：** 为 Heading 显式定义并保留 ID 属性，规定新增标题 ID 的生成及重名规则，增加“内容 → 编辑器 → 内容”的往返测试。不要靠重新生成所有 ID 修复，那仍会破坏已有链接。

**验收：** 编辑标题正文或相邻段落后，已有 ID 保持；预览和发布后的片段链接均可定位。自动化证据见 AUD-04。

## AUD-05：文字对比度没有达到预期

axe-core 4.14.0 检查了 23 个公开页面，以及菜单、深色/高对比度、主要后台界面等共 **32 个页面状态**。全部 23 个公开页面都至少命中页脚对比度问题；这些是重复出现的共享样式问题，不应夸大成 23 个独立 bug。

| 位置/状态 | 测得对比度 | 普通文字目标 |
| --- | ---: | ---: |
| 首页 News 日期，`#bbbbbb` / `#fafaf8` | 1.83:1 | 4.5:1 |
| 默认页脚，`#aaaaaa` / `#fafaf8` | 2.22:1 | 4.5:1 |
| 浅色高对比度模式下的页脚 | 1.91:1 | 4.5:1 |
| 深色高对比度模式下的 Accessibility 标题 | 2.49:1 | 4.5:1 |
| Admin 的部分内容摘要文字 | 2.89:1 | 4.5:1 |

普通文字至少 4.5:1、大号文字通常至少 3:1，是此次判断采用的 WCAG AA 标准。实际应按字号、字重和元素用途判断；报告没有把所有装饰图形都当作普通文字。[W3C 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**影响：** “有高对比度按钮”不代表高对比度模式全部有效，也无法据此验收 Lighthouse Accessibility 100。公开站有些浅色文字沿用了原有视觉语言，本轮没有将它们一律认定为新引入的回归。

**位置：** `packages/presentation/src/styles/design.css`、`accessibility.css`、`components.css`，以及 `apps/studio/editor/studio.css`。具体选择器、前景/背景颜色和节点保存在 axe 原始结果中。

**建议修复：** 先补全高对比度模式和 Admin 的颜色令牌。对于默认公开 UI，用户要求肉眼保持原样，而部分现有颜色达不到 AA，两项目标存在实际冲突：后续应提供仅调整问题文字明度的对照稿供选择。本轮未擅自改变公开配色。只修高对比度模式也不能把默认模式宣布为 AA 全面通过。

**验收：** 默认、深色、高对比度、深色加高对比度分别检查；人工复核自动工具的 `incomplete` 项。自动扫描不是完整的辅助技术验收。

## AUD-06：全中文申请卡使用英文语言声明和朗读参数

**复现：** 打开 `/woaidumuyibeizi/`，读取 `document.documentElement.lang`，结果为 `en`。点击 Read Aloud，用测试替身记录传入语音接口的中文片段，`utterance.lang` 同样为 `en`。

**原因：** 公开模板和后台预览都固定写入 `<html lang="en">`，朗读逻辑直接沿用根元素语言。页面模型没有语言字段。首页辅助中文名字已有单独的 `lang="zh-Hans"`，但这不能解决申请卡页面的问题。

**影响：** 浏览器和辅助技术收到错误语言信息，可能使用错误的发音规则。此次验证的是声明与调用参数，没有声称已在每台设备上听到错误发音。[W3C 页面语言说明](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html)

**位置：** `apps/site/src/pages/[...path].astro:17`、`apps/studio/server/index.tsx:165`、`packages/presentation/src/behavior/accessibility.ts:122`。

**建议修复：** 为页面设置明确语言，公开模板和预览统一读取；朗读按内容语言选择参数，混合语言内容按需分段。它只改变语义和朗读配置，可以保持视觉不变。

**验收：** 英文页面仍为英文，中文申请卡为中文；实际用 VoiceOver、TalkBack 或系统语音确认内容能正确朗读。

## 其他发现：不混同为上述 6 个已确认 bug

- **P3 语义改进：** Research、Teaching、归档等存在从 H1 跳到 H3 的情况。axe 将 `heading-order` 标为最佳实践问题；不能直接把这一规则的命中等同于 WCAG AA 违规。可在保持外观的前提下改进语义层级。
- **编辑能力缺口：** 文章模板中的固定 `12:00:00`、版权年份和许可文字没有对应后台字段。主体区块可编辑，但“所有显示内容都可以通过后台管理”尚未完全落实。若继续显示时间，应有真实时间数据，而非固定占位值。
- **操作体验待完善：** 富文本链接使用浏览器 `prompt`；素材复用仍主要依赖复制 URL；部分失败信息展示内部字段路径。后台结构已改善，但“Apple 级易用性”没有可据以宣称完成的用户任务测试。
- **手机导航可发现性：** 390px 截图中菜单初始只显示前三个入口；Media / Blog 位于横向滚动区域。CSS 允许横滑，所以不能称为链接丢失，但没有明显提示告诉用户还有选项，值得在保持现有风格的前提下改善。
- **质量门禁缺口：** 现有 CI 未包含这次新增的异常操作用例、axe 检查和 Lighthouse 预算。修复后应把有意义的回归用例纳入默认套件，而不是永久只放在独立审计目录中。
