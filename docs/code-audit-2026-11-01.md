## 二、审计新发现的缺陷（全部已修复）

| 优先级 | 问题 | 修复 |
| --- | --- | --- |
| P2 | Markdown 中输入不安全链接，会把整篇文章压成一个纯文本段落，并被自动保存 | 保留最后一个有效文档并提示用户改正；源码未能应用时，不允许切回富文本视图 |
| P2 | 全文检索每个词、每次按键都对全文重新规范化 | 每篇文章只规范化一次，查询词去重，并在索引加载后的空闲时间预热（数据见下） |
| P2 | Markdown 序列化时，**紧跟在带链接公式后面的普通文字也会被加上链接**（Tiptap 处理非文本节点标记的缺陷，会损坏内容）。解析时，链接、粗体、斜体也会从公式上丢失 | 序列化前，公式先以私用区占位符的形式放进普通文本节点，由 Tiptap 成熟的文本路径输出标记，最后再替换回公式；解析时，标记也会作用到公式节点 |
| P3 | 字面量 `$x$` 文本经过一次 Markdown 往返会变成公式；句中的 `$$` 会截断段落 | 只有在会被识别为公式时，才把文本中的 `$` 写成 `\$`，正文价格保持原样；块公式只在行首开始 |
| P3 | 每个文章页渲染“上一篇/下一篇”时都重新提取全部全文，静态构建是 O(n²) | 排序使用不读正文的 `publishedArticles()`；`articleIndex()` 按内容快照缓存 |
| P3 | Pages 概览卡片忽略列表的年份/月份筛选 | 只统计列表实际显示的文章 |
| P3 | 代码语言选择器中 `plaintext` 重复出现（React key 重复） | 语言名称改为单一列表，并由测试保证它与 lowlight 的 `common` 一致 |
| P3 | 每次保存都通过修改 iframe 的 `src` 刷新预览，会在浏览历史中逐条添加记录，浏览器“后退”会翻回旧预览 | 改用 `location.replace()` |
| P3 | 公开站全站运行时脚本 gzip 后达 6.2 KB，超过构建审计的 6 KB 预算，CI 会失败。原因是只有部分页面用到的申请卡、Firebase 管理、Medium、相册、News 控制器被每个页面加载 | 这些控制器改为只在含对应模块的页面按需加载。全站运行时降到 3.4 KB；页面在加载完成前离开时，不会再启动控制器 |
| P3 | 构建审计按 `script[src]` 直接读文件，带 `?v=` 版本号的脚本会读取失败（由本轮资源版本号引入） | 读取前去掉查询参数 |
| P3 | 编辑器里的图片加载前不占位置，加载后下方文字整体下移；此时点击可能误选图片，随后输入会替换掉它（CI 中 IND-05 由此暴露） | 新增迁移 `0006`，为 `assets` 表记录图片尺寸：上传时保存，旧图片在读取列表时分批补全。编辑器从构建清单、图片列表或上传结果取得尺寸，给 `<img>` 设置 `width`/`height`，加载前即预留空间。最终显示尺寸不变。新增 IND-09：拦住图片下载时，图片已占好最终高度，加载后图片和说明文字位置都不变；去掉修复时该测试会失败 |
| P4 | CSRF 令牌比较不是恒定时间 | 新增 `sameSecret()` 恒定时间比较，并有单元测试 |
| P4 | 图片相关组件层层传递从未使用的 `run` 参数 | 从 `ImageTools` 及全部调用处移除 |

- **Firefox `spawn UNKNOWN` 的根因**：我的工具进程运行在隔离的沙箱文件系统中，Playwright 的 Firefox 在里面无法解析其私有程序集 `mozglue`。在本机真实环境中，Firefox 与 WebKit 安装后都能正常启动。这与网页无关。
- **审阅时 WebKit 的 45 秒超时**：本轮完整运行中没有再出现。
- **5 条测试只修正了测试本身**：
  - 3 条过时断言：手机端按钮图标、账户菜单顺序、自定义下拉的选择器。
  - IND-06 原本假设手动保存一定早于 1.2 秒的自动保存，WebKit 较慢时不成立。现用 Playwright 时钟固定时序。
  - Firefox 报告 450.00003 px 这样的亚像素高度，断言改为允许极小误差。
- **2 条 Firefox 失败经诊断不是网页缺陷，按实际原因修正测试**：
  - 强制加载未使用的 `font-display: optional` 字体（名字字体只在首页使用并预加载）时，Firefox 会拒绝，而不是延迟下载。测试的本意只是等字体稳定，因此改为 `allSettled`。
  - 文章列表测试在 Firefox 中约有一半概率失败。网络记录显示新预览文档已加载、其脚本已执行，但 Playwright 的 Firefox 驱动仍在查询旧 frame。另写的探针从父页面读取 iframe 的实时 DOM，4/4 正确。该断言改为读取实时 DOM。

### GitHub CI（Linux）中的 WebKit

PR 首次运行 CI 时，Chromium 与 Firefox 全部通过，Linux 上的 WebKit 有 21 项超时或失败，两次运行结果完全相同。CI 改为逐条打印失败测试名，再用只跑失败项的临时诊断任务逐步定位：

- **卡住的原因**：每次界面变化后，下一帧都要渲染好几秒，Playwright 一直等不到元素“位置稳定”，点击最终超时。页面既没有卡死，也没有布局死循环（`ResizeObserver` 回调与 DOM 变更均为 0）。
- **逐项关闭渲染特性做对比**（每项都用全新页面，CSS 在应用加载前注入，只影响测试页面）：

  | 条件 | 切到 Page settings | 再切到 Content |
  | --- | --- | --- |
  | 正常 | 8.9 s | 超过 43 s，超时 |
  | 1× 像素密度 | 5.0 s | 31.6 s |
  | 去掉折射层 | 10.4 s | 超时 |
  | 去掉其他 CSS 滤镜 | 2.0 s | 12.7 s |
  | **去掉背景模糊（backdrop-filter）** | **2.6 s** | **1.3 s** |

- **结论**：CI 的 Linux WebKit 没有 GPU，液态玻璃的背景模糊全部由 CPU 计算。真实设备上的 Safari、Chrome 都用 GPU 合成，访客不受影响。
- **修复只针对测试环境**：共享测试夹具 `tests/fixtures.ts` 只在 Linux CI 的 WebKit 中关闭 `backdrop-filter`，产品 CSS 一行未改。Chromium、Firefox 与本地 WebKit 仍渲染并检查真实的玻璃效果；检查模糊数值的 3 条断言只在这一环境中跳过。修复后 Linux WebKit 89 项中 88 项通过，用时 10.9 分钟。
- **另外 3 处时序问题，均只修改测试**：
  - 页面外壳测试会收到 Apple 播放器自身的报错，现改用本地替身。
  - IND-05：字体晚到时，点在图片说明上的一次点击可能落到图片上，随后输入的文字会把图片替换掉。现在确认光标已在说明文字里才开始输入。
  - MOD-06：等 Markdown 源码区按内容撑高之后再滚动纸面。
- **CI 也改得更快暴露问题**：失败测试逐条打印名称和错误；浏览器测试步骤最多运行 20 分钟；累计 10 次失败即停止，不再逐个超时空等。
